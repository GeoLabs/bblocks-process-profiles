# prov_synth

Produces a **synthetic view** (a readable SVG diagram) of the provenance of an OGC API – Processes job run by
ZOO-Project-DRU. It works directly from the job's CWLProv 0.6.0 research object (Turtle) and uses no external
rendering service.

## Usage

```bash
python3 prov_synth.py BAG_OR_ZIP -o out.svg [--format svg|dot] [--profiles map.yaml] \
        [--json model.json] [--title "..."] [--show-platform-params] \
        [--no-dataflow] [--params none|summary|full] [-v]

# examples
python3 prov_synth.py job-2378/.../prov -o out/water-bodies.svg \
        --profiles examples/water-bodies-profiles.yaml --json out/water-bodies.json
python3 prov_synth.py job-2378/.../prov -o out/water-bodies.dot.svg --format dot \
        --profiles examples/water-bodies-profiles.yaml       # also writes out/water-bodies.dot

# secret-leak self-test (runs every format on each bag, greps outputs, logs and --scan paths)
python3 prov_synth.py --self-test BAG1 BAG2 --profiles examples/water-bodies-profiles.yaml --scan out
```

`BAG_OR_ZIP` can be a BagIt research object, a `.zip` of one, or a bare directory of `*.cwlprov.ttl` files.
The tool starts from `primary.cwlprov.ttl` (in a bare directory, from the document that no other document
references) and follows `prov:has_provenance`. It maps `arcp://uuid,…/metadata/provenance/<file>` IRIs to local
files, preferring `.ttl`, then `.nt`, then `.jsonld`.

Requirements: Python ≥ 3.10, `rdflib`, `pyyaml` (only for `--profiles`), and the Graphviz `dot` binary (only for
`--format dot`; without it, only the `.dot` source is written).

* `--format svg` (default): direct SVG with a deterministic layered layout in the W3C PROV visual language.
  Activities are blue rectangles, entities yellow rounded boxes and agents orange house shapes. Each provenance
  document gets its own grey band, headed with its name and the API path it is served at (`/jobs/{jobId}/prov`
  or `/jobs/{jobId}/prov/{provDocument}`). The primary band holds the agents row, the job row, the wrapping run
  with its inputs, the steps and the result; each nested document's band holds its steps. Steps wrap onto new
  rows when they do not fit. A legend and a footer naming the job close the diagram.
* `--format dot`: Graphviz DOT with one cluster per provenance document, rendered to SVG locally.
* `--json`: the intermediate model, already redacted.
* `--no-dataflow`: do not draw the step-to-step data-flow edges. They stay in the JSON.
* `--params none|summary|full` (default `summary`): how parameter passing from parent runs to steps is shown inside
  the step boxes.
  * `summary` gives one line, `params: aoi, band ∈ bands, epsg, item ∈ stac_items`.
  * `full` gives one line per input, `band ← node_water_bodies.bands (member) ×4`.
  * Platform parameters are counted, not listed, unless `--show-platform-params` is given.

## What is extracted

| Model part | Source |
|---|---|
| job: id, process id, server URL, job URL, start/end, `zoo:namespace`, status | ZOO-Project-DRU additions to the primary document, and `metadata/zoo/job-status.json` |
| agents and delegation chain | `prov:Agent`s (excluding container-image agents), `prov:actedOnBehalfOf` |
| document tree | `prov:has_provenance` (duplicates merged, see below) |
| runs per level | the `wfprov:WorkflowRun` of each document (for the primary document, the one `wasInformedBy` the job) |
| steps | activities started by the run (`prov:qualifiedStart/prov:hadActivity`). They are grouped by base name (`node_crop`, `node_crop_2` … become `node_crop ×4`). Each step records its plan IRI(s), container image(s) (`cwlprov:image`), first start and last end, and its nested document. Its CWL class, `run` target and `scatter` come from `workflow/packed.cwl` |
| scatter of a sub-workflow | one activity id with several `qualifiedStart`s is counted as N iterations |
| main inputs | `qualifiedUsage` of the wrapping run: role → literal `prov:value`, `prov:Collection` members, `ro:Folder` basename/entries, file basename |
| final outputs | entities generated by the wrapping run (`qualifiedGeneration` with role `…/primary/<name>`), plus the step that generated them |
| output data flow (`flows` in the JSON) | Each final output is traced back across levels. The tool takes its generating step(s), the entities those steps *used* that were themselves generated by another step, then the steps that generated those, and so on (depth ≤ 4). Entities are joined across documents by IRI. Each link records the relation (`wasGeneratedBy` or `used`), step, role and document, and whether it sits on the step activity (`step`) or is an output of the enclosing (sub-)workflow run (`run`). Folders are summarised from their dictionary members |
| step-to-step data flow (`dataflow` in the JSON) | **data** edges A → B: an entity, or a member of a collection/dictionary used by B (followed through `hadMember`, `hadDictionaryMember`/`pairEntity`, and matched by content through `specializationOf` to `urn:hash::sha1:` data), was generated by step A and used by step B, at any level and across documents (joined by IRI). A container that is itself generated by a step is the direct source; its members are not followed. Repeated or scattered instances are collapsed into one edge that records the output port, input port, entity kind, number of distinct entities and basenames. `through` lists the sub-workflow outputs the data also left by. **param** edges: an input of a run used by one of its child steps (same entity, same content, or a member of it); when the parent run did not record the input, the next ancestor run is used and a `note` says so |
| notes | anomalies found while reading (see "Data observations") |

**Output data flow (Water Bodies).** Two entities sit behind the final result. The node_stac step (in the app document)
generates the local STAC catalog folder `urn:uuid:3a9a6d55-…` (catalog.json plus one sub-folder per scene). The app
run also generates it, as its output `stac`. stage_out_0 (in the primary document) *uses* that folder and generates
`urn:uuid:aa3ac487-…`, a dictionary `{value: s3://…/catalog.json, type: string_format#URI}` that references the
staged-out copy. The wrapping run also generates `aa3ac487` (role `primary/stac`). In the SVG:
* the folder is drawn next to node_stac as "data produced by the Application", with `wasGeneratedBy` → node_stac;
* stage_out_0 → folder is drawn as `used (stac_catalog)`, crossing from the primary band to the app band;
* the result is drawn as "result · stac — reference to the staged-out copy", with `wasGeneratedBy` → stage_out_0
  and → the wrapping run.

The DOT output has the same edges, plus a dotted edge for the run-level `wasGeneratedBy` of the app run.
convert-url1 shows the same pattern: convert → folder `a7ed4c78` → used by stage_out_0 → s3 reference `5ba83123`.

**Step-to-step data flow (Water Bodies).**

| from | output | to | input | what |
|---|---|---|---|---|
| node_crop (×4) | cropped | node_normalized_difference | rasters | 4 files (crop_green.tif, crop_nir.tif), through the `rasters` collection members |
| node_normalized_difference | ndwi | node_otsu | raster | 2 × norm_diff.tif |
| node_otsu | binary_mask_item | node_stac | rasters | 2 × otsu.tif, through collection members; also left the sub-workflow as `node_water_bodies/detected_water_body` |
| node_stac | stac_catalog | stage_out_0 | stac_catalog | folder; drawn through the "data produced by the Application" entity, not as a separate edge |

In the SVG, data edges are thick teal arrows labelled `output → input · count`, in lanes below the rows. An edge
between bands goes through a corridor to the right of the bands (node_otsu → node_stac). Labels sit above their lane
when they fit between the two verticals, otherwise below it. Parameter passing is written inside the step boxes
rather than drawn as arrows, so the diagram does not turn into a hairball. The DOT output has the same data edges
(`constraint=false` across documents).

**Duplicate nested documents.** When several documents describe the same activity (for example
`workflow_20node_water_bodies.*` and `workflow_20node_water_bodies_2.*`), they are loaded and merged by RDF
union. The document with the most triples is kept as canonical. The comparison (strict subset, or N extra
statements) is reported in `notes` and in the band header. Start/end times are de-duplicated by value, so the
union does not double-count iterations.

## Redaction (always on; it cannot be turned off)

* Values bound to roles or JSON keys matching `(?i)(secret|password|token|access_key|aws_access|credential)` are
  replaced with `[redacted]`. Before anything is emitted, the tool scans every document and `primary-job.json` for
  these values. Once a value is known to be secret, it is redacted everywhere it appears, whatever its role.
* Any value matching `\.svc\.cluster\.local` (in-cluster endpoints) is replaced as a whole.
* After extraction, the whole model is scrubbed again. SVG, DOT, JSON and the `-v` log are all built from that
  scrubbed model.
* Stage-in/stage-out plumbing parameters (`STAGEIN_*`, `STAGEOUT_*`, `process`) are left out of the inputs box and
  only counted. `--show-platform-params` shows them, still redacted.
* `--self-test` collects the known secret strings of each bag: secret-role values, secret keys of
  `primary-job.json`, and in-cluster endpoints. It then checks that these strings appear in the raw primary
  document (a control showing the detector works). Next it generates SVG, DOT and JSON with
  `--show-platform-params` and `-v`, captures stdout/stderr, and greps all of them plus the `--scan` paths. It fails
  (exit code 1) on any match, and only ever prints sha256 prefixes of the secrets.

## Process profiles (`--profiles`)

```yaml
title: bblocks-process-profiles (D101)
subtitle: ospd.process-profiles.water-bodies.*
mappings:
  - {step: node_crop, profile: ospd.process-profiles.water-bodies.crop,
     openeo: "closeMatch load_collection + filter_bands", phase: data retrieval}
  - {image: "*/crop:*", profile: ..., openeo: ...}   # match by container image
  - {step: "stage_out_*", profile: null, note: "added by the platform"}
```

Entries match a step by base or instance name (`fnmatch`), or by container image (`fnmatch`, or a plain substring).
The first matching entry wins. Each matched step gets a green `≙ <short name>` tag, and a right-hand column lists
the profiles in file order, with their kind (CWL class plus the optional `phase`) and their openEO relation. The
column states that the mapping comes from the command line and is not asserted in the served provenance. Entries
that match nothing are reported in `notes`. Without `--profiles`, the diagram has no tags and no column.

## Limitations

* Only the RDF serialisations are read: `.ttl`, `.nt` and `.jsonld`. PROV-JSON, PROV-XML and PROV-N are ignored.
* Turtle has no named graphs, so the `bundle` blocks visible in PROV-N (directory descriptions) are not available.
  Directory content comes from `prov:hadDictionaryMember` instead.
* `prov:hadMember` is unordered in RDF, so collection members are sorted alphabetically. The order of the CWL
  array is lost: in Water Bodies, `stac_items` is shown S2A first, then S2B, which is not the job order.
* cwltool timestamps carry no timezone, while ZOO-Project-DRU job times are in UTC. The tool assumes naive
  timestamps are UTC, which is true in the observed bags.
* Step boxes show what the provenance states (repetitions, images, times, scatter inputs). Domain explanations such
  as "2 scenes × 2 bands" or "NDWI per scene" cannot be derived.
* The output-flow trace (the entity boxes) follows only entities that a step generated as a whole. The finer
  step-to-step data flow (teal edges) covers collection members.
* Scatter inputs are not recorded on the scattered sub-workflow's run. In Water Bodies, `node_water_bodies` has no
  `item` usage, so `node_crop`'s `item` is matched on the Application run's `stac_items` (member), and a note records
  this. Which scene went to which iteration cannot be read from the run itself.
* Pairing across iterations is not reconstructed: edges are aggregated per step base name. The data shows that
  `node_normalized_difference` (first instance) used the crops of `node_crop_3`/`node_crop_4` (S2A), and
  `node_normalized_difference_2` used those of `node_crop`/`node_crop_2` (S2B). The JSON aggregate does not keep this.
* Data-flow lanes are placed below a band's last row. With wrapped rows, a vertical from an upper row can cross a box
  of a lower row.
* In the SVG, a flow entity is placed right after its producing step. A `used` arrow from another band is routed
  through a lane above the entity's row. Many cross-band flows would make these lanes busy.
* The "local STAC catalog" wording is a heuristic: a produced folder that contains `catalog.json`.
* The agent row is not wrapped, so a very long delegation chain widens the diagram. Step rows do wrap.
* The `≙` tags reflect the mapping file only. The provenance itself has no profile or activity-type assertion.

## Data observations (reported as `notes`)

* The job resource entity is typed `wfdesc:ProcessRun`, a class wfdesc does not define (`wfprov:ProcessRun` is the
  run class).
* The cwltool agent is the subject of `prov:qualifiedStart` (`wasStartedBy`), which PROV-DM defines for activities
  only.
* Plan IRIs of step runs differ from the declared `wfdesc:hasSubProcess`: `main/main/app` against `main/app`, and
  `main/water-bodies1/node_water_bodies` against `main/node_water_bodies`. In addition, `node_crop_3` and
  `node_crop_4` have no prospective plan.
* `workflow_20node_water_bodies_2.*` is a strict subset (415 of 507 triples) of `workflow_20node_water_bodies.*`.
  Both are referenced via `has_provenance` from the same scattered activity.
